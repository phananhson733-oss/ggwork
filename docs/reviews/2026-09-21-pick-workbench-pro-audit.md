## A. 最可能返工的五处

1. **持久化配置含糊。**源码有内存 checkpoint 回退，旧配置优先于统一数据库配置。首版选单实例持久化存储，同时验证会话、运行、候选和选择恢复；刷新不等于重启验收。

2. **把身份当工具参数。**上游已有鉴权，不必重做；新增工具必须从服务端身份取 owner，逐对象检查资料、会话、结果的归属，不能接受模型指定用户。

3. **规则、数据和解释漂移。**Markdown 不是硬过滤器。人工固化版本化过滤及排序；结果冻结批次、知识版本、条件和证据。上下架仅代表快照时点，不能称实时。

4. **序号保存缺少稳定合同。**“第1、3部”须绑定历史结果与不可变项ID，不能取最新列表。双击重试、重复选剧、提交成功但回包失败，要分别处理。

5. **四工具不等于四权限。**上游装配还会追加内建、MCP、ACP工具。最终工具集及执行端都要白名单，禁止借通用工具绕过过滤或保存授权；每轮调用设上限。

## B. Clone 后保留与修改

保留Web壳、鉴权、会话/消息/运行存储、流式通信、工具调用机制；不抽出harness另搭聊天系统。修改工作区壳、侧栏及聊天结果入口，新增独立选剧业务模块。现有工作区已将侧栏和内容区域组合，可沿此入口改造。

工具使用`config.tools[].use`入口；业务路由/服务可接`ExtensionRegistry.routers/service`。整仓SHA、锁文件和扩展API一起锁：已核实API为`0.2.1`，源码明确1.0前次版本可破坏兼容。不能以release标签推断功能。

## C. 最小数据与调用合同

**身份：**首版`workspace_id=已认证user_id`，不建团队表；业务记录带owner，引用runtime的thread/run/message，不复制消息库。线程元数据保留当前result_id。

| 记录 | 最小内容 |
|---|---|
| 剧库批次 | 来源、快照/导入时间、原文件/hash、导入状态 |
| 剧库行 | 批次、来源命名空间＋来源剧ID、剧场/语言/标签/上下架、信号值/来源/观测窗口；同批重复ID拒绝，同名不合并 |
| 知识版本 | 原文、来源、版本/hash；硬规则另存版本化配置并关联知识 |
| 候选结果 | 会话/运行/消息、父结果、批次/知识/规则版本、完整条件/排序、固定项ID/名次/原行/证据 |
| 个人选择 | 用户＋稳定来源剧身份唯一，关联历史结果项 |
| 保存命令 | 命令ID、用户确认、规范化参数hash、提交回执 |

`search_knowledge`返回版本及段落引用；`query_candidates`只收类型化条件，不收SQL，服务端过滤排序，**先保存快照再返回**。硬条件缺失不算满足；不足N如实返回，失败不报零候选；无发布记录则状态未知，不能据此筛“未发”。

追问继承父结果条件并应用增删改，生成新结果；歧义先澄清。请求绑定父结果，晚到响应不替换当前卡片。`get_drama_detail(result_id,item_id)`读取对应历史快照。

`save_selection(result_id,item_ids,command_id)`：卡片选择后确认，或聊天序号解析后展示剧名确认；服务端将命令绑定用户/会话/结果/项。资料和模型调用不能授权。一次确认沿重试复用命令ID，不用tool_call_id替代。

**同一事务写选择及回执**：同键同参返回原回执，异参409；跨批次重复选择由稳定来源身份去重。提交后断线按命令查询回执，不靠聊天文字判断成功。删除会话不级联删除已选。

### 审计回复二

结论：赞成完整 clone 后定制，但不赞成“改 UI＋加四个工具”就视为闭环。以下基于指定提交 `29d2857` 的源码静态核查，不代表已有部署、数据接入或测试通过。

### A. 最可能返工的五个问题

1. **把个人空间当成界面分组。** 上游项目仓储按用户隔离，但显式 `user_id=None` 会跳过用户过滤。新增工具若用它兜底，隔离即失效。身份必须来自认证上下文，缺失即拒绝；`project_id` 不能代替所有权校验。

2. **把“来自 CSV”当成证据可信。** 还缺来源剧ID唯一性、信号口径、观测时间、缺值和失效策略。导入先校验再整批启用，保存原文件哈希；同名不合并，必需字段未知不得通过硬过滤。Markdown 是解释材料，不是可执行规则：硬条件和排序须有服务端版本，证据不足不能凑满N部，也不能称“未发”。

3. **连续追问依赖模型记忆。** 重排、重试、多标签页或上下文压缩都会让“第1、3部”漂移。每次查询生成不可变结果；提交追问时绑定历史结果ID，序号立即解析成项目ID。改条件生成子结果，保留完整生效条件；歧义先澄清，禁止默认套用最新列表。

4. **把调用保存工具当成用户授权。** 资料文字、模型解释或自动重试都不能授权。卡片保存按钮即授权；聊天保存指令先显示明确剧名并确认。授权必须绑定用户、会话、结果及项目集合，模型不能自行生成有效授权。

5. **把会话持久化等同业务恢复。** 上游支持数据库存储，也存在内存分支，不能仅验证聊天刷新。候选先提交业务库再展示，保存先提交再回执；运行失败不得抹掉已提交选择，恢复不得重新执行保存。

### B. clone 后如何改

保留认证、会话/消息、流式传输、运行状态、checkpoint 和数据库生命周期；业务表独立迁移，不复制聊天存储。首版采用单实例、单 worker、持久化 SQLite及数据目录。

修改左导航和聊天容器，增加固定候选面板、资料导入和“我的选剧”；新增业务服务及四个工具。工具经 `tools[].use` 加载；源码会额外追加内置工具，必须在最终装配处验收白名单，而非只改提示词。

扩展合同已有 `routers/service/middlewares`，没有通用 `register_tool` 方法，不应臆造接口。锁定完整提交与依赖锁文件，不用“v2.0.0”代替主干基线。

### C. 最小数据与调用合同

个人空间直接绑定认证 `user_id`，暂不建团队/成员表；所有业务读写、关联校验及缓存均带所有者。

六类业务记录足够：

- **导入批次**：来源、哈希、导入时间、校验状态；**剧条目**：批次、来源命名空间＋来源剧ID、业务字段、逐项信号来源/观测日期。
- **知识版本**：文档ID、版本、原文、来源、哈希；**候选结果**：用户、thread/run、父结果、完整条件、批次ID、知识版本、规则版本、固定排序及项目证据。
- **个人选择**：剧键、来源结果/项目、保存时间；**保存请求**：授权范围、确认状态、幂等键、载荷哈希、回执。

`search_knowledge` 返回版本及原文片段位置；`query_candidates` 接收类型化条件和历史结果引用，返回结果ID、实际数量、证据及不支持的条件；`get_drama_detail` 按结果/项目读取对应快照，不偷换最新版；`save_selection` 只接受服务端确认过的保存请求。

追问先将条件补丁合并为完整条件，再执行校验。未明确切换批次/规则时沿用原版本；换版本创建新结果。右栏只消费已提交结果。模型解释必须引用证据ID，通过固定 schema 校验，不能创建候选事实。

保存事务内校验身份、确认范围及项目归属，再写选择和回执。**同键同载荷返回原回执，异载荷返回409**；唯一约束“用户＋剧键”防止从不同结果重复选剧。保存失败显示失败，不以聊天里的“已保存”为准。
