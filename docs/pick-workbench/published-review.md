# Private published review and manual plan links

`GET /api/pick/feedback/posts` reads immutable owner-private snapshots without refreshing Feishu. An authenticated configured owner can filter by exact feedback account record ID, channel, language and UTC publication dates, with stable publication-descending/post-key-ascending pages of at most50. Unlinked and un-attributed are separate states. No version/source yields unavailable/disabled/auth_required with null totals; successful empty filters yield0. Raw source warnings and source coverage remain visible. Shared catalogue storage never receives private feedback.

A review row uses one actual latest observation timestamp. A metric last observed earlier is unknown on this row rather than mixed into the newer snapshot. Measured0 remains0. Observation age comes from actual publication/observation timestamps. Conflicting publication timestamps leave publication age unknown and the window incomplete. The default7-day threshold is readiness only; cumulative8/30-day values are not D7 performance or comparable fixed-age increments. There are no inferred rates, sums or denominators. Only post-grain `post_rs` source entries from exact release references appear beside that post, keeping currency/attribution unknown as supplied. Drama/account/CPS totals are never copied to each post, even after manual plan attribution.

No verified cross-system GGWork plan-row ID propagation exists. Automatic linkage remains inactive. A user must select both a real post and an owned saved plan row and explicitly confirm. Known channel, language, theater or resolved full-identity contradictions block confirmation. V1 exactSD/owner-confirmed bindings and V2 master bindings use the same conservative resolver as review display; raw declarations cannot bypass failed or ambiguous binding, while a differing explicit confirmed declaration remains a negative constraint. Existing language aliases use the shared normalization without rewriting full identity. Plan account free text and feedback linked-record account ID are different namespaces. The UI displays this limitation and disables unsupported account-specific follow-up; it never sends the latter as a mirror account name.

`POST /api/pick/feedback/plan-links` validates PlanLinkCommand, exact owner/plan/row/revision and feedback snapshot. It then rechecks current relationship evidence and fences source pointer, current catalogue pin and owner identity mappings in the receipt transaction. Owner-scoped writes serialize across processes; primary keys enforce one current post claim and one command receipt per owner/request. An authenticated owner can retry a committed command even after source disablement or reconfiguration; only new confirmations require current source eligibility. A repeated command returns its immutable receipt; changed payload under the same request ID conflicts. A different target for an attributed post conflicts and preserves the existing link. A source release reidentified as another post cannot create a second attribution. Several posts may belong to one plan row.

Original receipts and structured source/plan/binding evidence live in immutable private command records. Explicit reconfirmation of the same target may publish a new current receipt, leaving earlier commands and their retries intact. New source or plan revisions produce a current confirmed/needs_review/conflict projection; no GET overwrites a historical receipt. Metric-only changes or equivalent reordered release rows preserve association. Identity/account/channel changes, missing posts, lost/ambiguous bindings or changed plan revisions require review. Disabled or unauthorized sources leave owner-owned links auditable as needs_review, without claiming fresh revalidation.

Private migration0011 adds `ggwp_feedback_plan_links` and `ggwp_feedback_plan_link_commands` after0010. Public/anon/authenticated/mirror-reader roles receive no access. Host cookie authentication and CSRF still guard HTTP writes; no model write tool or external write is registered. Source normalization and identity binding run off the event loop; HTTP reads/confirmation are bounded, and unknown write outcomes use the same request ID for recovery.

Evidence is synthetic: dual SQLite/PostgreSQL public API, real loopback Gateway ordinary-user sessions/CSRF, and actual TypeScript completion-api HTTP requests. These do not establish production source propagation, activate a provider, prove live model behavior, or close the later full browser/task acceptance gate.
