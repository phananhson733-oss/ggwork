# Trends 阶段 0：本机两天运行与报告（TR-05）

代码：`ggwork_pick/observe/trends/stage0*.py`；对照清单格式 `trends-stage0-controls-v1`，任务清单格式 `trends-stage0-plan-v1`。设计 4.9、4.11；计划 TR-05、第 8 节、D20、D23、D39。状态文件与密钥见 `trends-state.md`，客户端见 `trends-client.md`。

阶段 0 不是测限流。它回答三件事：Trends 看不看得见 GSC 看得见的剧（闸门 A）；本机直连会话拿不拿得到相关查询与 userType（闸门 B）；真实回答长什么样（接口核实）。结论决定颗粒度（H、D 或 H+D）、N、滞后、trend-rules-v1 全文，以及计划第 8 节的四种去向选哪一种，由 G2 审定。

## 预算与时间

- 两天合计至多 180 次请求，每天至多 90 次，预热、explore、multiline、相关查询与重复获取都算。现在的清单是第一天 88 次、第二天 84 次；每天给重试留的余量很少，所以市场序列排在最后，额度用完时先砍它们。
- 这两个上限运行时都会执行，不只在生成任务清单时核对：每天的 90 次由状态文件里的预算管；两天合计的 180 次按两天的 `requests.jsonl` 累加，某一天换了几个目标日重跑都算在内，到了 180 次就拒跑（退出码 2）。一个单元要等当天额度够它全部的请求才开始，不会发出 explore 之后才被额度截断。
- 一次会话只建一个客户端（一个连接池），预热和所有单元都走它，和以后的 cron 一样；第二天那个 POST 的重复单元也在同一个客户端上，按单元指定方法。
- 每部剧各取小时级 `now 7-d` 与日级 `today 1-m`，一个词一个请求。标了 `related` 的对照在日级单元上顺带取相关查询；种子只取相关查询。每天把当天第一部正对照的小时级序列隔 6 个单元再取一次：第一天用 GET，第二天用 POST，顺带核实 explore 两种方法都答。
- 目标日按 D23：UTC 02:00（北京时间 10:00）起到次日 01:45 属于下一个目标日，01:45 之后到 02:00 不发请求。第二天须在比第一天晚的目标日运行，也就是第一天之后、至少过了一次北京时间 10:00。
- 限速与熔断照 TR-03：每个请求发出前先等限速器和熔断器，再预留额度并保存状态；429 暂停至少 30 分钟再试探，验证码或同意页当天熄火，其余单元记未覆盖。按模拟时钟估算，一天约 25 分钟（实际等待以限速器为准，遇到暂停会更久）。

## 步骤

以下在仓库的 `customizations/pick-workbench` 目录执行，`PY` 指后端虚拟环境里的 python。状态密钥按 `trends-state.md` 准备，`export PICK_OBS_STATE_KEY_FILE=…`。

1. **生成任务清单**（不联网）：`$PY -m ggwork_pick.observe.trends.stage0 plan`。某一天开跑后再生成会被拒（退出码 2）；要重来，先把 `runs/`、`raw/` 移走。
2. **核对**（不联网）：`$PY -m ggwork_pick.observe.trends.stage0 run --day 1 --dry-run`，列出待跑单元、请求数、geo 与方法。
3. **第一天**：`$PY -m ggwork_pick.observe.trends.stage0 run --day 1 --init-state`。只有第一次运行带 `--init-state`。中途被打断（包括长暂停时按 Ctrl-C）就不带它重跑，已完成的单元不再请求；被打断的那次会话照样记进 `meta.json`，标 `interrupted`，报告里能看到它的代理、熔断和首次限流。单元在截止时刻被半路截断时，结果行记下已经发出的请求。
4. **中期报告**：`$PY -m ggwork_pick.observe.trends.stage0 report`。两天都有观测（至少一个单元发出去并拿到回答）才定稿；否则出中期报告，标「待第二天」（或「待第二天补跑」：跑过但一个单元都没观测到，比如第一个请求就遇到验证码页）的结论都是暂定，路线不给：闸门 B 要两次会话都稳定；闸门 A 按一半的正对照暂判（至少 4 部才判定）。
5. **第二天**（晚一个目标日）：`$PY -m ggwork_pick.observe.trends.stage0 run --day 2 --pace user`。`--pace` 选限速节奏：`design`（默认）是设计 4.2 的包络，约每分钟 4 次；`user` 是用户实测的节奏，连发至多 4 次、持续约每分钟 2 次（桶容量 4、每分钟补 2，其余与 TR-03 相同）。第一天按 `design` 跑，约 14 分钟后吃到第一个 429，降到半速后一路无事，所以第二天改用 `user`，顺带验证这个节奏能否撑满一整次会话。是否跑过第一天、第一天是哪个目标日，先看 `meta.json`，没有时再看第一天的 `results.jsonl` 与 `requests.jsonl`（进程被直接杀掉时不会写 meta）。
6. **定稿报告**：`$PY -m ggwork_pick.observe.trends.stage0 report`，拿到 U5 后加 `--manual <文件>`（可重复），给出手工导出与抓取序列的秩相关 ρ（≥0.6 为形状一致）。浏览器时区默认 UTC+8（`--utc-offset-minutes 480`）；中文界面导出的「天 / 时间」与全角标点也能读。`--n` 改日级可见的非零日下限，报告里本来就有 N=6、9、12、15、20 的对比表。
7. **脱敏夹具**：`$PY -m ggwork_pick.observe.trends.stage0 fixtures --day 1`（第二天同理）。剧名换成 `stage0 <组> <序号>`，相关查询换成稳定的假名，widget token 换成 `REDACTED_TOKEN`，像 IP 地址的串换成 `192.0.2.1`。原始存档不留响应头（Location 的查询串里可能有剧名，Set-Cookie 是密钥），回放要用的两个头按记录重建：重定向的 `location` 按记下的类型与主机重建（验证码页 `https://<主机>/sorry/index`、同意页 `https://<主机>/`，不带查询串），`content-type` 按正文推断（HTML、JSON 或纯文本）。这样回放出来的状态与真实回答一致（重定向判 `blocked_redirect`，HTML 判 `html_body`）。人工看过再挑几份替换 `tests/fixtures/trends` 里的构造夹具（`constructed: false`），并把对应的 `pending_stage0` 条目核掉。

`--root` 可以换产物目录（测试就是这样做的）。

## 报告里有什么

结论一览；输入与来源（含 GSC 导出的时效说明：小时级 now 7-d 看不到那时的需求，日级 today 1-m 能覆盖）；每次会话的请求数、熔断事件、是否被中断与代理；闸门 A（H、D 各一行）与 N 的敏感性表；逐个对照的非零小时/非零日与相关查询；闸门 B；第 8 节的去向；滞后（按 isPartial 的位置回标，小时级取看到的最大值）；接口核实（点数、isPartial 位置、time 类型、userType、空响应、GET/POST、重复获取的差异、相关查询与 Breakout）；U5；选定颗粒度的 trend-rules-v1 全文与占位参数；选 D 或 H+D 时的数据合同变更单（D39）；还欠什么。

判定口径：

- 请求失败或没发出去的单元一律写「未观测到」加原因，不当作零，也不进可见率的分母（前提 1）。回答被解析了、却找不到裸剧名那条线的，记 `line_missing`，同样算未观测到。
- 可见：小时级最近 144 个完整小时里非零 ≥12；日级最近 30 个完整日里非零 ≥N，默认 N=12（与小时级下限对应：四个 7 天块每块至少 3 个非零日）。完整点不够窗口的序列按实际点数判，标「窗口不足」，闸门 A 表里单列个数（设计 4.9 说 `today 1-m` 是 30 个日点、去掉末尾 partial，真实回答可能只有 29 个完整日）。
- 闸门 A：已观测的精确剧名正对照（`exact_title`）可见 ≥50%，且估算每天非泛词判定 ≥5 条（A 档约 60 部 × 地区对照可见率；H+D 时减半重算）。正对照观测不到 8 部（中期报告 4 部）不判定。查询词与剧名不完全一致的正对照（`query_mismatch`，现在的清单有 1 部）单列，不进分母。
- 这个估算偏宽，报告里写明，交 G2 定：12 部地区对照里 1 部可见就够 5 条；没有扣掉泛词剧；用「可见」（规则 2 的充分性）代替「能判定」。报告另给一列严格估算：地区对照里 B1–B4（日级 W1–W3）每块非零 ≥3、上升规则判得动的比例 × A 档剧数，只作参考，不进闸门。
- 闸门 B：每次会话都稳（没有被熔断熄火，也没有单元被熔断跳过，按 `meta.json` 与结果行判），要了相关查询的单元里可用 ≥80%，发出去的种子至少一个拿到列表，有回答的 explore 都带 userType；两次会话都要过。某天跑过却一个相关查询或一个种子都没发出去，闸门 B 未定，不略过那一天。
- 路线（第 8 节）：两天都有观测、闸门 B 定稿、两个闸门都判定了才给；否则写「未定」和缺什么。
- 颗粒度：H 过选 H；只有 D 过时，小时级仍看得见 ≥25% 的正对照选 H+D，否则选 D；都不过则规则全文不定稿。选 D 或 H+D 时的数据合同变更单写明冻结输入 `frozen_inputs.granularity` 取合同的值（`"D"` 或 `"HD"`；报告里的 H+D 就是合同里的 HD）。

## 出口与代理

阶段 0 在本机跑，D20 的出口开关不开，不发任何探测请求。会话开始时按 httpx 自己的读法检查这次请求会不会经过代理（`stage0_proxy.py`，只在本机读，不联网）：

- httpx 默认信任环境，经 `urllib.request.getproxies()` 取代理：只要设了任何 `*_PROXY` 环境变量（不分大小写），就只看环境变量；一个都没设时，退回读系统代理设置（macOS 的网络设置，Clash、Surge 开「系统代理」就写在这里；Windows 读注册表）。
- `meta.json` 的 `proxy` 记四样：设了的代理变量名（`HTTP_PROXY`、`HTTPS_PROXY`、`ALL_PROXY` 及小写）、设了的绕过变量名（`NO_PROXY`，它不是代理，单列）、系统代理设置了哪些协议（http、https），以及实际生效的是哪一种。只记名字和协议，不记地址（值里可能有账号）。
- 报告按生效的那种写：环境变量或系统代理生效时，写明请求经过代理、出口在代理那一端；都没有时写「未设代理环境变量，也没读到系统代理」，并注明 TUN 类 VPN 在这之下转发，本机无从判断。不写「本机直连」。

## 对照清单的来源（需要你确认一次）

`controls.json` 是 2026-09-25 在本机建的，输入有三样：GSC 手工导出 `gsc-2026-09-03`（查询与网页两张表）、RealShort 仓库 `src/lib/editorial-picks.ts`，以及 **RealShort 生产库的只读查询**。本批的共同规矩写的是「不碰生产库」，这次读取当时没有在回报里说明，这里补上，请你确认是否在授权范围内：

- 查了什么：`dramas`（剧名、语种、group_key、章节数、上架与同步时间，用来把 GSC 查询词对到剧、选正典条目和近期上架的地区对照）；`catalog_rows`（剧名、平台、语种、上架/下架日期、是否有信号，用来挑下架剧与地区对照候选）；`cps_bill_daily` 与 `outbound_clicks` 只取了按剧汇总的计数（历史订单数、近 7 天外链点击数），用来给候选排序；另读了一次 `information_schema.columns` 看 `catalog_rows` 的列名。全部是 SELECT，没有写。
- 怎么保证只读：连接时设 `default_transaction_read_only=on` 与 `statement_timeout=60s`，连上先 `SHOW default_transaction_read_only` 断言为 on，每次查询后回滚；连接串从 scratchpad 里的私有 env 文件读，不打印、不进 git。
- 什么时候：2026-09-25 约 09:45–10:00 UTC（北京时间 17:45–18:00），最后一次在 10:00:29 UTC，即 `controls.json` 的 `built_at`。结果只留在本机的产物目录与 scratchpad，仓库里的 `canary_controls.json` 只有身份键与 geo。
- 以后要身份键，不再直连生产库：走 TR-07 的正对照（GSC 导出）、当前共享批次，或者工作台镜像。

## 退出码

| 退出码 | 情形 |
|---|---|
| 0 | 完成；`--dry-run`、`plan`、`report`、`fixtures` 正常结束 |
| 1 | 当天跑了，但有单元没覆盖（额度、熔断或截止时刻）；看输出里的原因，同一目标日重跑只会补还能补的 |
| 2 | 拒跑，一个请求都没发：没有对照清单或任务清单、清单在生成任务清单后改过、没设密钥、第二天早于第一天或在同一目标日、两天合计已发满 180 次 |
| 3 | 状态文件不存在（首次运行忘了 `--init-state`）、被别的进程占用，或读不出来；见 `trends-state.md` |

出错信息只写类名与我们自己的说明，不回显命令行参数，也不打印 HTTP 原文。
