# 人工决定（`ggwp_obs_decisions`）

生效链的实现是 `ggwork_pick/observe/decisions_state.py`（TR-35，计划 D12、D24、D43）；写入路由 `POST /api/pick/obs/decisions` 归 TR-25。本页是运维主题文件（计划 D35），索引由 TR-29 收录。

## 生效规则（值守时要知道的）

- 采集服务发布集合时，读到当时最大的决定 id，记作 `decisions_version` 冻结进集合。所以一条决定要等该通道的下一个集合才生效，已经发布的集合永远不变。
- 对应确认按（身份、平台、规范化标题）记，每个身份只认最近一次。撤销会清掉确认。确认之后只要变过一次，这条确认就永久失效：某个共享剧库批次里平台或规范化标题变了、身份不在批次里（别名或上游 id 换了身份）、中间有批次明细已清理核对不了，或者有人手动配对把这个身份当旧身份配走。之后标题改回、别名配回，都不会自动恢复，只有再确认一次才恢复（G3 评审 P2-2）。
- 失效记录由 Trends 采集服务每个会话开头算出，冻结进集合的 `frozen_inputs.lapsed_confirmations`（决定 id 列表），下一个集合在它的基础上累加。所以：失效在该通道下一个集合才体现；已经发布的集合不变；某条确认为什么失效，查它的决定 id 最早出现在哪个集合的这一列，再看那次会话读到的批次。Trends 连续几天没有发布集合时，中间的批次可能已被清理，这段时间里所有确认都会按「核对不了」失效，需要重新确认。
- 平台为空的行确认不了（合同要求平台至少 1 个字）。资料页（TR-24、TR-25）对这种行不要给确认按钮（点了只会被 422 拒绝），而是提示「平台未知，先补全来源资料」：在来源数据里补上平台、重新同步进共享剧库之后，这一行才能确认。不要填「unknown」之类的占位平台绕过合同。
- 人工加入最多 50 条生效。已经不在当前共享批次的条目、已经换了别名的条目，也占名额，要撤回（`active=false`）才会释放。资料页会标出不在当前批次的条目。
- 人工加入、暂停、歧义改判都记在写入时的那个身份上，不会随别名转到新身份。歧义改判也不会因为改标题而失效。
- 别名确认、拒绝、手动配对不在这里生效，而是由 gsc 服务在每轮第 0 步写成新的别名版本（D43）。
- 写入一次只进行一条：gateway 在写入事务的第一句加锁，PostgreSQL 上是 `LOCK TABLE ggwp_obs_decisions IN SHARE ROW EXCLUSIVE MODE`。这把锁不挡读，所以采集服务和资料页照常读。但如果有人手工开事务往这张表插了行、一直不提交，gateway 的写入会一直排队。手工操作这张表时要尽快结束事务。以 deerflow_app 连接时，空闲事务 5 分钟后会被断开（`idle_in_transaction_session_timeout`）；以其他角色连接没有这个上限。

## 决定表出现无法应用的行

**症状**
- 两个 cron 在读决定这一步以退出码 3 退出，消息以「ggwp_obs_decisions 第 N 行」开头，只写行号和出错位置，不带内容。
- 写决定的路由对所有决定都报错，包括用来纠正的撤销：写入前要先读出有效状态，读不下去就什么都写不进去。

**先只读地看一眼**（以 deerflow_app 或 pick_observer 执行，把 N 换成消息里的行号；`payload_json` 可能带备注原文，不要贴进工单或聊天）：

```sql
SELECT id, kind, owner_id, request_id, created_at FROM ggwp_obs_decisions WHERE id = N;
```

**按消息分两种处置**
1. 「kind 不在合同的九种之内」：新版 gateway 写入了旧采集服务还不认识的种类。把认识它的镜像部署到两个 cron 服务（D5：gateway 与两个 cron 同步重部署，新增种类时采集服务先上）。这一行本身没有问题，不要删。
2. 「payload_json 与 kind 列不一致」，或「不合合同：位置（错误类型）」：这一行不是经 gateway 写的，可能是手工 SQL，也可能是合同改动后旧数据不兼容。决定表只追加，改行要先经用户批准。批准后，以 deerflow_app 在一个事务里把这一行改成合同的形状，或者先导出备份再删除，并把行号、原因、改法记进 progress.md。改完 gateway 立刻恢复，cron 在下一次触发时恢复。

已经发布的集合不受影响：判定行冻结在集合里，不回查决定表。
