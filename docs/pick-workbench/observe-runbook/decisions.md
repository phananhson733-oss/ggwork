# 人工决定（`ggwp_obs_decisions`）

生效链的实现是 `ggwork_pick/observe/decisions_state.py`（TR-35，计划 D12、D24、D43）；写入路由 `POST /api/pick/obs/decisions` 在 `ggwork_pick/observe/decisions.py`（TR-25b）。本页是运维主题文件（计划 D35），索引由 TR-29 收录。

## 写入接口

- 请求体是合同第 12 节的九种决定之一。操作人取自登录身份，请求体里不能带；没登录、身份是 default 或共享身份都拒绝。路由先认人再读请求体，没登录的请求连请求体是不是 JSON 都得不到回答。
- 回答：
  - 201：新追加了一行，回 `{"id", "kind", "request_id", "created_at", "replayed": false}`。
  - 200：同一操作人用同一 `request_id` 重发了同样的内容，回原来那一行，`replayed` 为真，不再追加。
  - 401：没登录。
  - 409：人工加入已满 50 条生效（消息说先撤回一条），或者这个 `request_id` 已经用于内容不同的决定。
  - 422：请求体不合合同。回答是 `{"message", "problems"}`，`problems` 最多 5 条，每条写成「位置（错误类型）」，例如 `watch_add.geo（string_pattern_mismatch）`；多出来的键写成 `<extra>`，kind 不对写成 `kind（union_tag_invalid）`，不是 JSON 写成 `body（json_invalid）`。回答里不重复请求的任何原文。
  - 413：请求体超过 16 KB（一条决定只有几百字节）。
  - 503：决定表里有读不了的行（见下文「决定表出现无法应用的行」），这时重发旧请求也是 503；或者选剧服务还没就绪。
- 一条决定要等该通道的下一个集合才生效（见下一节）。`b_only` 下 Trends 不跑观察清单、不做逐剧判定，对应确认、暂停、人工加入写进去之后暂时没有采集服务读（计划 TR-25 的 2026-09-30 说明）；资料页也还没有这三种操作的按钮。

## 生效规则（值守时要知道的）

- 采集服务发布集合时，读到当时最大的决定 id，记作 `decisions_version` 冻结进集合。所以一条决定要等该通道的下一个集合才生效，已经发布的集合永远不变。
- 对应确认按（身份、平台、规范化标题）记，每个身份只认最近一次。撤销会清掉确认。确认之后只要变过一次，这条确认就永久失效；之后标题改回、别名配回，都不会自动恢复，只有再确认一次才恢复（G3 评审 P2-2）。会让确认失效的有四种：
  - 某个共享剧库批次里，这个身份的平台或规范化标题变了。
  - 某个批次里没有这个身份：别名或上游 id 换了身份，也可能只是上游漏了这部剧。经 accept-empty 发布的空批次会让全部确认失效。
  - 要核对的批次里有明细已被清理的，核对不了：全部确认失效。
  - 有人手动配对，把这个身份当旧身份配走：决定一写入就清掉，即使 gsc 的别名刷新之后拒掉了这次配对（例如会成环），确认也不会回来。
- 失效由 Trends 采集服务在每个会话开头算出，记成一份账本，随计划存进这个会话的批次行（`ggwp_obs_batches.plan_json` 的 `notes.lapses`），不管这个会话最后有没有发布集合。下一个会话从最近一份账本接着累加，只读那份账本读到的批次之后新发布的共享批次。发布集合时，账本里的决定 id 冻结进 `frozen_inputs.lapsed_confirmations`。所以失效在该通道下一个集合才体现，已经发布的集合不变。
- 什么时候会出现「核对不了」：共享剧库保留最新 3 个批次，以及 30 天内被候选集引用的、被镜像配对的批次，其余的明细会被清理。两次 Trends 会话之间如果出现超过 3 个没被引用的新批次，最旧的就可能被清理。一天两次定时拉取不会触发；一天里多次内容有变化的手动同步，或者 Trends 停跑几天，就可能触发，这时所有确认都要重新点一次。
- 查某条确认为什么失效：账本对每条失效记了原因和批次 id。原因有四种：changed（平台或标题变了）、absent（批次里没有这个身份）、unverifiable（批次已清理，核对不了）、carried（只知道 id，没有原因）。会话日志里也有一行「对应确认新失效 N 条（平台或标题变了 a、批次里没有这个身份 b、批次已清理核对不了 c），累计 K 条，读到共享剧库批次 …」。只读查看最近三份账本（以 deerflow_app 或 pick_observer 执行）：

  ```sql
  SELECT id, target_date, outcome, plan_json -> 'notes' -> 'lapses' AS lapses
  FROM ggwp_obs_batches WHERE channel = 'trends' ORDER BY target_date DESC LIMIT 3;
  ```

  账本读不回来时，Trends 服务以退出码 3 退出，消息写「批次 … 的对应确认失效账本读不回来」。不要删这一行或把 `lapses` 改成更早的账本，那样会让它记下的失效复原；先把行号记进 progress.md，经用户批准后按账本格式（`trends-lapse-ledger-v1`）修好这一行。
- 确认按钮取的是最新已发布集合判定行里的平台与规范化标题（TR-24、TR-25），不是实时剧库。失效判断只知道批次的先后，不知道确认是在哪个批次之后点的，要核对的批次都算，包括确认之前发布的。确认取自集合时，下一个窗口从那个集合的会话读到的批次之后开始，不会误伤；取自实时剧库时，窗口里更早的旧标题批次会让刚点的确认直接失效。
- 平台为空的行确认不了（合同要求平台至少 1 个字）。资料页（TR-24、TR-25）对这种行不要给确认按钮（点了只会被 422 拒绝），而是提示「平台未知，先补全来源资料」：在来源数据里补上平台、重新同步进共享剧库之后，这一行才能确认。不要填「unknown」之类的占位平台绕过合同。
- 人工加入最多 50 条生效。已经不在当前共享批次的条目、已经换了别名的条目，也占名额，要撤回（`active=false`）才会释放。资料页会标出不在当前批次的条目。
- 人工加入、暂停、歧义改判都记在写入时的那个身份上，不会随别名转到新身份。歧义改判也不会因为改标题而失效。
- 别名确认、拒绝、手动配对不在这里生效，而是由 gsc 服务在每轮第 0 步写成新的别名版本（D43）。
- 写入一次只进行一条：gateway 在写入事务的第一句加锁，PostgreSQL 上是 `LOCK TABLE ggwp_obs_decisions IN SHARE ROW EXCLUSIVE MODE`。这把锁不挡读，所以采集服务和资料页照常读。但如果有人手工开事务往这张表插了行、一直不提交，gateway 的写入会一直排队。手工操作这张表时要尽快结束事务。以 deerflow_app 连接时，空闲事务 5 分钟后会被断开（`idle_in_transaction_session_timeout`）；以其他角色连接没有这个上限。

## 决定表出现无法应用的行

**症状**
- 两个 cron 在读决定这一步以退出码 3 退出，消息以「ggwp_obs_decisions 第 N 行」开头，只写行号和出错位置，不带内容。
- 写决定的路由对所有决定都回 503，包括用来纠正的撤销和重发的旧请求：写入前要先读出有效状态，读不下去就什么都写不进去。回答只说去看本页，gateway 日志里有一行 `[pick-obs] a decision was not appended`，后面是同样的「ggwp_obs_decisions 第 N 行…」。

**先只读地看一眼**（以 deerflow_app 或 pick_observer 执行，把 N 换成消息里的行号；`payload_json` 可能带备注原文，不要贴进工单或聊天）：

```sql
SELECT id, kind, owner_id, request_id, created_at FROM ggwp_obs_decisions WHERE id = N;
```

**按消息分两种处置**
1. 「kind 不在合同的九种之内」：新版 gateway 写入了旧采集服务还不认识的种类。把认识它的镜像部署到两个 cron 服务（D5：gateway 与两个 cron 同步重部署，新增种类时采集服务先上）。这一行本身没有问题，不要删。
2. 「payload_json 与 kind 列不一致」，或「不合合同：位置（错误类型）」：这一行不是经 gateway 写的，可能是手工 SQL，也可能是合同改动后旧数据不兼容。决定表只追加，改行要先经用户批准。批准后，以 deerflow_app 在一个事务里把这一行改成合同的形状，或者先导出备份再删除，并把行号、原因、改法记进 progress.md。改完 gateway 立刻恢复，cron 在下一次触发时恢复。

已经发布的集合不受影响：判定行冻结在集合里，不回查决定表。
