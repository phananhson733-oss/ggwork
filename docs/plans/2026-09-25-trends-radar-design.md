## 0. 结论

**关于「要不要经 RealShort 中转」：我同意不经中转，但有三样东西仍然只能来自 RealShort。**
- Trends 和 GSC 都是第三方观测，由工作台自己的 Railway 定时任务直接采集，写进工作台自己的 Supabase。理由：RealShort 那边没有合适的存储（`catalog_signals` 每次剧单导入先删后插，RS:scripts/import-catalog.ts:185-187），也没有合适的运行环境（它的同步路由配置 600 秒，Vercel 函数按套餐最长 800 秒起，放不下几个小时的限速会话），GSC 接入也缺小时、页面×国家、完整性这些维度（RS:src/lib/gsc-api.ts:104-109）。
- 仍然只能来自 RealShort 的：
  1. **剧目身份**：走现有 feed。工作台不重算。
  2. **旧页解析结果**：当前 GSC 点击有 49% 落在旧站遗留页上。RealShort 的真实规则是先按 URL 里的 slug 查、查不到再按旧 id 查，还有 locale 以表为准、下架剧转博客等人工回退（RS:src/lib/legacy-redirect.ts:129-183）。工作台不复刻这套逻辑，而是消费 RealShort 用自己的解析器算好、带版本的「旧 URL → 目标」结果。
  3. **GSC 属性的授权**：Search Console 属性归站点所有者，要由 Owner 把工作台的服务账号加成用户。这只是授权，不经 RealShort 的应用或数据库。
- 趋势结论目前的**落地出口**在 RealShort：运营把剧填进「编辑精选」Google 表格，跑 `pnpm sync-editorial` 重写 `src/lib/editorial-picks.ts`，再提交、部署才上首页货架。这张表 12 条里有 6 条的依据是「Google trend 上热度持续上升」。工作台产出按这张表列合同排好的一行，运营复制粘贴即可。这是人工桥，不是数据中转。
- 决策 5（plan:91）建议补一句适用范围，原文和改写见 1.2。

**方案骨架**：两个 Railway cron 服务（Trends 每天一个长会话；GSC 每 3 小时一轮）→ 工作台 Supabase 的观测表（迁移 0007）→ 每次发布一个不可变的「观测集合」，集合里冻结判定所需的全部输入版本 → 智能体在一次运行里同时钉住剧库批次和观测集合 → 资料页与智能体只读集合里的判定行。

**最大的不确定性，也是第一道闸门**：Trends 逐剧轮询到底能不能看见真实需求。现有证据偏悲观：脚本包旧缓存里 75 条 7 天小时序列，66 条在 144 小时里非零不到 12 小时，只有 4 条是密的，其中 3 条是泛词；一部 GSC 证实有真实搜索的保语剧，在全球口径下被判成噪声。所以第一版先过「阶段 0」的两道闸门（4.11），再定 Trends 的颗粒度、判定线和投入。

**gpt-6-astra 多轮反驳后收紧的五处**
1. **身份**：标题匹配出来的别名只进待确认队列，不自动归并；自动接收只限有稳定上游 ID 的情形。命中的剧要人工确认对应关系才进正式推荐。
2. **GSC 完整性**：水位不等于明细完整，未满额也不等于没漏行。改成切片版本整体切换、每份响应算可用区间、全站同口径总量加逐剧过滤请求两层准入，过不了就只出描述性标签；从不断言真实零曝光。
3. **业务含义**：删掉「需求驱动 / 排名驱动」这类因果标签；双涨、退潮拦截只在同一个国家内成立，全球只作并列；页面语种不再当国家用。
4. **版本冻结**：集合里记下剧库批次、别名版本、旧页解析版本、市场表、规则、联动规则、排序版本；资料页和智能体只读判定行，不回查会被覆盖的明细表。
5. **提前量**：提示单独留存 180 天，所有满 14 天的提示都进分母，未兑现和滞后的都算，不只统计成功样本。

**可以作为实现计划的输入。** gpt-6-astra 第五轮判定剩余问题全部闭合、没有新的 P1。起草实现计划时要带着四个前提：
1. 「未观测到」的语义要贯穿资料页、智能体和联动，任何地方都不能简称为「零」。
2. 两份下界一致只是准入规则，不证明数据完整，也不证明统计独立。
3. 逐剧核对要和实际判定的国家、窗口、页面集合、dataState 对齐；「相差不超过 10%」的分母和取值口径要在实现计划里写死。
4. Vh、Vd 的覆盖、失败和陈旧状态都要验收；14 个 PT 日的证据不齐时，不出 7 天正式标签，也不出对应的联动。

**交付**：两个通道同期交付，基础开发约 35 人日，RealShort 侧的旧页解析导出另计约 1.5 人日。这是「阶段 0 与金丝雀都通过」前提下的估算，阶段 0 之后按选中的数据合同重估。日历上还要加阶段 0 约 2 天、金丝雀约 11 天、影子运行 2 周、提前量复盘 4 周起。上生产要等 0005/0006 随 P2 上线。

## 1. 三个决定的落实

### 1.1 两个通道都要
- **分工**：Trends 负责站外提前发现，以欧美为主；GSC 负责站内曝光加码。两者按剧目身份并排展示，只在同一个国家内联动（第 6 节）。
- **边界**：GSC 只看得到本站有页面的剧，也就是 ReelShort 行，约占欧美六语候选池的 31%〔市场调研〕。其余剧场的剧只有 Trends 这一路外部信号。
- 两个通道共用同一套观测集合、钉住规则和资料页，智能体的两类条件同时开放。

### 1.2 不经 RealShort 中转

| 数据 | 走法 | 理由 |
|---|---|---|
| Trends 观测 | 工作台直连采集、直接存储 | RealShort 没有合适的存储与运行环境 |
| GSC 观测 | 工作台用专用只读服务账号直连 | RealShort 的 `GscRow` 只存 key、点击、曝光；两边钥匙可以分别吊销 |
| 剧目身份 | 仍走 feed 只读 | source_id = base64url(rowKey)（RS:src/lib/pick/feed-map.ts:314-317）；只有 ReelShort 前缀的行能解出 CPS book_id |
| 旧页解析 | 第一版用 RealShort 解析器算好的一次性导出；之后换成 v2 新资源 `rs_legacy`（新合同，不会随 P2 自动获得） | 正典规则与旧链接规则只能有一份实现 |
| 落地出口 | 资料页生成按编辑精选表列合同排好的一行 | 运营现在就是这么做的 |

**决策 5 原文**（plan:91）：「数据只从 RealShort 流向工作台，走经过鉴权的只读 HTTP 导出接口（在 feed 上扩展）。工作台从不连接 RealShort 的数据库。」

**建议改写为**：
> 本条只约束 RealShort 的数据：只经鉴权的只读导出从 RealShort 流向工作台，工作台不连 RealShort 的库。第三方外部数据（Google Trends、Search Console 等）由工作台直接采集、存入自己的库，凭据只放在工作台的 Railway 服务上。这些数据对应到剧目时，只用 RealShort 导出的身份和解析结果，不在工作台重算。

RealShort 自己的日级 GSC 继续服务它的首页货架。它在 v1 feed 里的信号种类叫 `gsc`；本地 09-21 批次里一条 `gsc` 信号都没有，生产上是否一直为空要核实。工作台自己的观测叫 `obs_gsc`，两者分开标注，不互相比较。

### 1.3 全球与欧美（`market-map-v1`，带版本，冻结进集合）

| 展示分组 | Trends 实际查询的 geo | GSC 国家 |
|---|---|---|
| 全球 | en 查 WW | 全站合计 |
| 北美 | US（A 档） | USA、CAN |
| 英爱澳新 | 稳定期加查 GB | GBR、IRL、AUS、NZL |
| 西欧、南欧、中东欧 | es 查 ES；de、fr、it 查本国，首轮只做 B 档筛查 | 欧洲各国 |
| 拉美 | es 查 MX，pt 查 BR（A 档） | 拉美各国，紧挨欧美显示，不计入 |
| 保加利亚 | 首轮不进清单，阶段 0 抽样 | BGR 单列 |
| 菲律宾、印度 | 只在 WW 里看 | 只在全站合计里看 |

- **分组只用于展示**。Trends 的 US 不代表整个北美，GB 不代表英爱澳新。每条结果都写实际 geo；联动和拦截只按国家对上（6.1）。
- **这是范围选择，不是「数据证明没有量」**。上一版看板全部按全球查、失败写 0，它能说明「有」，说明不了「没有」。阶段 0 用 geo=BG、DE、FR、IT 各查一小批做对照。
- **不用页面语种推国家**：手工导出里 es 页面共 85 次点击，西班牙全站 11 次点击。两个数字的聚合口径不同（按页面计与按站点计），推不出 es 页面有多少点击来自西班牙。这正说明语种和国家必须分开，国家归属只看 page×country 数据。
- **站内现状**：去掉保加利亚后，欧洲加北美只占本站点击 18%、曝光 27%；曝光第一的国家是菲律宾（18.8%）〔GSC 调研〕。站内加码按欧美排序时基数很小，第 5.6 节的正式门槛按这个基数设计。

## 3. 总体架构

### 3.1 两个 Railway cron 服务
- 两个服务都用 gateway 的镜像，但**显式覆盖启动命令**（例如 `python -m ggwork_pick.observe.trends`），关掉 healthcheck，`restartPolicyType=NEVER`。配置文件写绝对路径（`/railway.trends.toml`、`/railway.gsc.toml`），否则会读到根 `railway.toml` 的 healthcheck。
- Railway cron 按 UTC 触发，上一轮没退出就跳过下一次，而且不会替你终止上一轮，程序必须自己按时退出（Railway Cron 文档）。触发不保证准到分钟，所以 02:00 是目标和监测指标，不是保证。

| 服务 | 计划（UTC） | 行为 |
|---|---|---|
| `pick-obs-trends` | 20:30–01:30 每 30 分钟触发 | 第一次触发跑完当天整个长会话；崩溃后下一次触发从持久状态恢复；01:45 硬截止并退出，目标 02:00（北京 10:00）前发布 |
| `pick-obs-gsc` | 每 3 小时第 25 分 | 10 分钟硬截止；顺带记录提前量里程碑 |

- **打包路径**：镜像里装的 `ggwork-pick` 来自 `backend/extensions/sources/ggwork-pick`（backend/pyproject.toml:116），不是直接复制 `customizations/pick-workbench/ggwork_pick/`（docker/Dockerfile.pick-gateway:11-12）。源码改动要经扩展管理器更新快照、锁文件一致后再构建。每次部署在镜像里自检三件事：`ggwork_pick.__file__` 指向快照、`collector_version` 与预期一致、迁移头与预期一致。
- **不改 gateway 的运行逻辑**：`service.py`、`sync.py`、`schedule.py` 不动。`python -m` 启动时 `gp/__init__.py:6-10` 有导入副作用，要改成延迟导入；这一处 gateway 也会加载，要和 P2-5c 协调。

### 3.2 批次、集合与预算桶
- **Trends**：每个目标发布日（02:00 UTC 截止那天）一个采集批次，`UNIQUE(target_date)`；一个批次发布一个集合。`window_end` 在批次创建时算好并持久化，午夜后恢复也不重算。
- **GSC**：每 3 小时一轮，每轮一个采集编号和一个集合，不按日期唯一。
- **每日预算桶**单独一张计数，和采集批次、发布集合分开。

### 3.3 并发控制：租约带代次
- 每个服务只用**一条** asyncpg 连接，每一步用完就释放，不开 ORM 池。熔断暂停可以长达 4 小时，不能一直占着会话。
- 租约放在 `ggwp_obs_runtime`：`lease_owner`、`lease_until`、`lease_generation`。接管时代次加一。
- **三个边界都在事务里锁住租约行再写**：预留请求预算、写入响应、发布集合。每一步开一个事务，先 `SELECT ... FROM ggwp_obs_runtime WHERE channel = ? FOR UPDATE` 锁住这一行，核对 owner、generation 和 `lease_until` 仍有效，再写业务行，最后提交。接管也要先锁同一行，所以接管和写入被串行化，旧进程不可能在接管之后提交。核对失败就说明已被接管，当前进程立即退出。SQLite 测试库用 `BEGIN IMMEDIATE` 达到同样效果。
- 预算在**发出请求前**扣减，超时、没收到响应、结果未知的都不退回。
- 续租间隔 60 秒，租期 5 分钟；熔断暂停期间照常续租。

## 4. 通道一：Google Trends

### 4.1 数据源：低频直连
- **客户端**：用 httpx 自己写，约 200 行，不新增依赖。流程：预热拿 NID cookie → explore 取 widget token → multiline（走势），按需再调 relatedsearches（相关查询）。一次 explore 只对应一个时间范围。响应先剥掉开头的 `)]}'`。参数固定 `tz=0`、`hl=en-US`。每次记录 `userType`、`isPartial`。
- **合同要靠真实响应核实**：字段形状、空响应、Breakout 表示、`userType` 取值、cookie 行为、YouTube 与网页搜索的差异，第三方供应商文档里有，不等于自写客户端能拿到。阶段 0 逐项核实，写进解析器的夹具。
- **不用 pytrends-modern**：它遇到 429 会连发重试、每次新建连接、随机换 UA，这正是脚本包被放大限流的原因〔直连调研〕。
- **条款**（只说一次）：Google 条款禁止违反 robots.txt 的自动访问，robots.txt 禁止 `/explore?`。这是用户已知的取舍。做法上不登录、不解验证码、不点同意页，页面注明「Data source: Google Trends」。

### 4.2 限速（按 HTTP 计，预热、探针、重试都算）

| 参数 | 值 |
|---|---|
| 并发 | 1 |
| 同一查询单元内的请求间隔 | 1.5–3 秒 |
| 查询单元之间 | 25 秒 + 0–10 秒随机 |
| 令牌桶 | 容量 8，每分钟补 4；活跃的一分钟 8–12 次，对应「4 部一分钟、停 1 分钟」 |
| 任意 60 分钟 | ≤200 次 |
| 分段 | 连续 40 分钟，整体空闲 10 分钟 |
| 实际平均 | 约每分钟 2.9 次（含空闲段） |
| 每日上限 | 金丝雀期 600；稳定期计划 ≤650，单日封顶 800，放宽要先把起跑时间提前 |
| 重试 | 429 不重试；5xx 或超时重试 1 次，间隔 30–60 秒；连续两次按限流处理 |

**依据**：脚本包按每分钟约 17 次请求连续跑，11 个「正常段」被限前的累计请求数分别是 160、40、2360、280、920、800、880、880、280、40、2440，其中 5 段不超过 280；恢复时刻集中在太平洋时间约 10:00 和 19:10。这更像按时段计的配额窗口，而不是简单的累计阈值。所以控的是每天总量和节奏，并且金丝雀每天记录「首次限流前的累计请求数和时刻」，用来区分这两种机制。

### 4.3 熔断
- **限流信号**：429；跳到 sorry 页或 consent 页；API 返回 HTML；403。
- **首次出现**：立即停，剩余请求记 `skipped_breaker`。暂停 30 分钟后发一次探针；成功按半速继续；失败暂停依次升到 60、120、240 分钟。
- **当天熄火**（任一条）：探针失败 3 次；当天熔断 3 次；累计 429 达 5 次；出现一次验证码或同意墙。
- **跨天**：连续 2 天熄火，次日上限减半；7 天内熄火 3 次，停用直连并告警。
- **状态必须持久**：暂停、熔断级别、当日计数、cookie 罐都存库（金丝雀期见 4.11）。**状态读不到时当天不跑**。否则崩溃重启后会用新 cookie 按全速重来，重演脚本包「50 秒冷静、换会话、再请求」的放大模式。

### 4.4 cookie 与出口
- 每个服务一个 cookie 罐，每天最多预热一次；被限时保留原罐（Google 会先拒新会话）。UA 固定，跟罐绑定。罐加密存放，密钥只配在 trends 服务上，不进日志。
- 出口 IP 逐请求记录，只做关联分析。Railway 默认出口是共享、会变的地址池〔直连调研〕；静态出口是 Pro 功能，地址也可能共享。数据中心 IP 会不会比住宅 IP 更容易被限，靠金丝雀判定。
- **要先问清你本机实测时的出口**：本机时区是上海，如果那次走的是 VPN，出口多半是多人共用的机房节点，结论不能当成住宅 IP 的结论。

### 4.5 每日容量与分配（约每分钟 2.9 次）
**单位**：一个**查询单元** = 身份 × geo × 查询形态 × 时间范围。取走势要 2 次 HTTP（explore + multiline），再取相关查询加 1 次。英语剧查 WW 和 US 是 2 个单元。

| 项 | 金丝雀期（≤600） | 稳定期（≤650） |
|---|---|---|
| 预热、探针、重试 | ~15 | ~20 |
| 大盘对照序列（每个 geo 1 个单元） | ~16 | ~20 |
| 种子发现（闸门 B 通过后） | ~56：8 个种子 × WW/US/GB + 4 组本地化，各 2 次 | ~90：再加 YouTube 属性 WW/US |

| B 档（2 天一轮） | 每天 35 单元 × 2 = 70 | 每天 50 单元 × 2 = 100 |

### 4.7 请求形态、判定线与身份证据
**判定线固定，变体只作证据，从不相加**
- **剧名清楚**：一个请求里放 `[剧名, 剧名 full movie, 剧名 drama, 剧名 episode]`，意图词按语种本地化。**判定只看裸剧名那条线**；变体线只用来算「带意图词的搜索占比」，作为身份证据。
- **泛词，或被更长的同语种剧名包含**：只放三个意图变体，不放裸剧名，否则会被剧名的背景量压成 0。每条变体线只作描述性展示，结果记「歧义，不判定（设计如此）」，资料页单独计数，不是缺陷。
- **同语种同名多行**（英语 59 个标题对应 125 行）：结果挂到所有同名行，标 `shared_title`，默认不进智能体。

**歧义判定三道**
1. 常用词表，只给下界。
2. 是否被更长的同语种剧名包含。
3. 剧名的相关查询（3 次 HTTP，14 天有效）：出现 lyrics、song、电影年份判泛义；出现平台名、episode、dailymotion 只说明「像短剧相关搜索」；没有相关查询记 `unresolved`，不当泛义，也不当已证实。

**身份证据等级**（`id_evidence`，带版本）
- 强：发现段里「平台种子 + 精确剧名」直接命中这一行。
- 中：剧名的相关查询里同时出现本行所属平台名。
- 弱：只有剧名本身。
- 同名检查只能在共享池内做，同平台的旧作、翻拍这类池外同名作品查不到，所以强与中也只是「对应证据」，不是实体认证。
- **正式推荐要求人工确认对应关系**：只对判出 rising 或 emerging 的剧弹确认，不审整张清单，预计每天个位数。确认一次对这个身份长期有效，改标题或换别名时重新确认。
- 未确认的：强证据显示为「推定对应」，只有显式要求时才进智能体；中、弱证据只在资料页显示。

**大盘对照**：每个 geo 单独请求一条对照序列（本地化的「short drama」），不和剧名放同一个请求。

### 4.9 判定规则 `trend-rules-v1`（阈值全部是占位值，影子运行后回标）
**先定颗粒度（阶段 0 决定，规则全文在阶段 0 报告里定稿，定稿前不写规则代码）**
- 方案 H：只取小时级 `now 7-d`，规则如下。
- 方案 D：日级 `today 1-m`（30 个日点）做充分性与上升判定；去掉末尾 partial 的那一天；用完整的 7 天块比较，抵消周内效应。小时级不取。
- 方案 H+D：两者都取，D 判上升，H 只给通过的剧补「日内实测非零小时」描述；两者冲突时以 D 为准。A 档容量减半。

**以小时级为例的规则**
1. **窗口**：整个批次共用一个 `window_end` = 批次创建时的整点减 3 小时，创建时持久化。取 [window_end−144h, window_end)，切成 B1–B6 六个 24 小时块。3 小时滞后值按金丝雀里 `isPartial` 的位置回标。窗口内缺小时或含 partial 点记 `insufficient_window`。
2. **只用相对量**：判定只用非零小时数和块与块的比值，不对自归一化指数设绝对门槛。
3. **`rising`**：B1–B4 每块非零小时 ≥3（保证基线中位数大于 0，不需要任何下限常数），B5–B6 非零小时 ≥12。设 r = min(B5 均值, B6 均值) ÷ median(B1..B4 均值)，要求 r ≥1.5；去掉最高那一小时后重算仍成立。对照序列用同一公式算出 r_c，要求 r ÷ r_c ≥ 阈值。对照序列要满足 B1–B6 每块非零小时 ≥3，这样 r_c 一定大于 0；不满足时 r_c 无定义，记 `control_unavailable`：资料页给未校正结果并标注，智能体默认不用。公式只用非零小时数和比值，整体乘以任何正数，结果都不变。
4. **`emerging`（从零起量）**：B1–B4 非零小时 ≤3；B5–B6 非零小时 ≥12 且 B6 非零小时 ≥8；单小时占比 ≤40%，去掉最高一小时仍成立。新剧没有基线，只看比值会一直判 sparse；它离隐私阈值最近、噪声最大，默认不进智能体。
5. **`cooling`（冲高回退，标准 §5.3）**：峰值块在 B1–B5 且该块非零小时 ≥12；B6 均值不到峰值块均值的 65%，且不到 B5 的 70%。只作拦截标签，只拦同一国家的「加码」建议。
6. **确认**：相邻两天的集合在各自窗口里都判 rising，而且两次观测可比，才记 `confirmed`；只有一天记 `first`。可比指：两次都是当天新采的有效观测（不是 carried_over）；`window_end` 前移了 20–28 小时；查询表达式、颗粒度、数据来源、规则版本与参数都相同；身份相同，或在冻结的别名版本里相连。确认记录保存两次的集合与判定行编号。同一会话末尾对 first 命中再取一次，只作**重复获取一致性检查**：两次形状明显不一致的，标 `unstable`，不进智能体。它不算独立样本。
7. **优先级**：failed/stale > ambiguous/shared_title/unresolved > insufficient/sparse > unstable > cooling > rising/emerging。
8. **不跨剧排名**。

**测试必须覆盖**：把序列整体乘以常数，标签不变；把低位的 1 和 0 互换几处，结果只在预期范围内变化；同一请求里加进一条更强的变体线，裸剧名线的标签不应翻转，翻转就说明依赖了绝对刻度。

### 4.10 失败与陈旧
- `fetch_status` 分 10 种，其中：`ok`（有完整序列）、`ok_zero`（序列完整但全是 0，按 sparse 处理）、`no_data`（HTTP 成功但时间轴没有点，不参与判定）。只有 `ok` 和 `ok_zero` 参与判定；失败不写值，不覆盖上一次成功值。
- 没刷新到的行沿用上次状态和自己的 `window_end`，标 `carried_over`，只在资料页显示；超过 3 天记 `stale`。
- A 档覆盖率低于 80% 不发布，上一个集合继续生效，资料页标红。
- 所有结果都显示「截至何时」。当前生效的 Trends 集合超过 26 小时，带趋势条件的查询返回「数据陈旧」而不是空结果，也不再给加码建议。
- 全零率逐日对比；`userType` 变化告警。

### 5.1 接入

### 5.3 切片、修订与可判定性
- **切片** = 数据集 × PT 日 × 形态。形态是「整日」或「按国家拆分」之一；同一个数据集和日期同时只有一个**生效版本**。
- **请求状态**与**可判定性**分开记：
  - 请求状态：`fetched`（HTTP 成功且未满额）、`truncated`、`failed`。
  - 可判定性：`usable`、`gap_exceeded`、`unverifiable`，由 5.6 的覆盖准入给出。
- **替换**：新版本全部写完后，在一个事务里把生效指针切到新版本，再删旧版本。整日和拆分两种形态不会同时生效，也不会混用不同轮次的行。新版本失败或截断时，旧版本继续生效，切片标陈旧。陈旧的切片不能用于正式判定：窗口只要碰到它，这一轮只出描述性标签。修订后消失的行随旧版本一起消失。
- **零的含义**：切片里没有某页的行，只说明明细里没有。GSC API 不保证返回全部数据行，按页面过滤的请求也不保证，所以本方案**从不断言真实零曝光**，只说「在 GSC 返回的数据里未观测到」。未满额不等于没有漏行，全站缺口小也不等于某部剧没漏。
- **每份响应存 metadata 和它的可用区间**，以本轮 A 的水位为锚：
  - A 自己缺 `first_incomplete_hour`：本轮不出正式 24 小时窗口，沿用上一轮。
  - PT 日结束得比 A 的水位早的切片：按官方合同缺这个字段是合法的，可用区间是整个 PT 日。
  - PT 日跨过 A 的水位的切片：应当有这个字段，可用区间到它为止；缺了与 A 矛盾，记 `watermark_absent`，这个切片本轮不可用。

### 5.4 窗口
- **共同截止**：H_c = min(A 的水位，A′ 可用时的 A′ 水位，最新那个 C 切片的可用区间终点)，转 UTC 取整点，H_c 所在小时也算未完成。历史切片的日末不参与取最小值。然后检查 [H_c−48h, H_c) 是否被 C 各切片的可用区间连续覆盖；有断口，本轮就不出正式 24 小时窗口。A 和 C 是独立请求，不是同一个快照，所以取保守值。
- **24 小时窗口**：W0 = [H_c−24h, H_c)，W−1 是再往前 24 小时。完整水位大约滞后 9 小时（一次观察）。
- **7 天窗口**：最近 7 个完整 PT 日对前 7 天，只取自 D、E。
- 水位之后的小时只标「暂定」，不进比较。

### 5.5 页面归因（以页面为主，查询只作证据）
- **新页**：尾部必须是 24 位十六进制，并且和 v1 `source_id` 解码出的正典 id、locale 一致；非正典 id 记 `noncanonical_unresolved`，镜像上生产后用 `rs_ids` 解析。
- **旧页**（占点击 49.4%）第一版就要归因。只做新页的话，308 跳转会把流量从旧页挪到新页，凭空造出「站内上升」。
  - **解析结果由 RealShort 算**：RealShort 新写一个导出脚本（那边仓库的改动，需你批准），完整走一遍线上的解析链，只算不跳转。先按 `next.config.ts` 的重定向归一（locale 别名、无前缀旧路径补 `/en`、`?id=` 形态，:98-106、:230-245），再走 `legacy-redirect.ts` 的先 slug、再 id 回退、locale 以表为准、博客回退。
  - 输入是近 90 天 GSC 里出现过的全部旧页 URL，按 GSC 返回的完整原串，含 `?id=` 这类查询参数，不做任何归一。
  - 输出是一个不可变快照，带 `snapshot_id`、解析时的 RealShort 提交与剧库状态、`resolver_version`、`as_of`。每条 URL 原串给出 `target_kind`（drama / blog / unresolved）、locale、book_id 或博客路径。换快照就换 `snapshot_id`，旧快照保留到没有集合引用为止。
  - 工作台用 GSC 返回的完整 URL 原串精确查表，不自己解码、不去查询参数、不比对 slug。`/en?id=38000` 和 `/en?id=49020` 是两条不同的键。查不到的记 `legacy_unmapped`；未映射的旧页点击超过旧页总点击的 2% 时，请 RealShort 重跑导出，直到 `rs_legacy` 上线。
- **一部剧的指标** = 新页 + 解析到它的旧页。解析到博客的旧页单列「已转博客」，挂在对应剧名下展示，不并入剧的总量。
- **映射变化不能造出涨跌**：一个集合里两个比较窗口必须用同一个解析版本；解析版本变了，映射带来的差额单列 `mapping_changed`，这部剧本轮不出上升标签。另外，某身份旧页占比在窗口间变化超过 30 个百分点的，标 `migration_suspect`，默认不进智能体。
- **站点级页面**：首页、博客、列表页记为站点级；查询 Q 只用于人工别名表与精确剧名匹配的「推断归因」，单独展示，不并入本剧总量。

### 5.6 覆盖三层
资料页常驻三层数字，不能只报第一层：
1. **已收明细内部守恒**：已归因 + 各类未归因 = 收到的明细合计。未归因分项：旧页未收录、目标已下架、非正典、locale 不符、站点级、编辑页、站外。
2. **明细缺口**：A′ 的总量减去 C 的明细合计。手工导出里三张表合计就对不上（国家表 860 次点击、网页表 953、查询表 518），说明明细天然有缺口，必须显示。
3. **不可知部分**：截断、失败、陈旧的切片数及其覆盖的时段。

**覆盖准入（两层）**
- **全站层**：24 小时窗口按小时比较 A′ 与 C 的合计（A′ 不可用时用 A″ 按 PT 日比较）；7 天窗口按 PT 日逐日比较 A″ 与 D、E 的合计，14 天都要比，A″ 与明细取同一个 dataState。缺口占比不超过 τ（初值 5%，影子运行回标）记 `usable`；超过记 `gap_exceeded`；两种总量都拿不到记 `unverifiable`。不是 `usable` 的窗口，所有剧只出描述性标签。
- **逐剧层**：全站层通过后，对将出正式标签的剧另发按页面过滤的请求：24 小时标签用 Vh，7 天标签用 Vd。GSC API 不保证返回全部数据行，过滤请求也不保证，所以过滤请求与明细汇总是两份独立的下界。两者在每个窗口相差不超过 max(10%, 3 次曝光) 才算一致，正式标签取两者中较大的值；不一致标 `detail_gap`，这部剧只出描述性标签。过滤请求失败同样只出描述性标签。
- 两层都通过，才出正式标签（5.8）和联动（6.1）；否则只出描述性标签，并注明原因。

扣除已下架剧后，可归因上限约为点击 56%、曝光 40%〔GSC 调研〕。

### 5.7 国家
alpha-3 国家码原样存。展示按 `market-map-v1` 汇总成分组，只给 24 小时和 7 天合计；小时曲线只画总量和分组合计。保加利亚单列，并标「保语页面 98.1% 的点击来自一部剧」（这是页面语种口径，不是国家口径）。

### 5.8 规则 `gsc-rules-v1`（单点透明：每个标签输出命中条件和原始计数）
**描述性标签**：资料页全部展示，按国家和全站分别算，24 小时完整窗口，带「暂定 / 完整」标记。

| 标签 | 条件（v9.5 原值作初始阈值） | 进智能体的正式门槛 |
|---|---|---|
| 曝光飙升 | W0 曝光 ≥2000，或 W0 对 W−1 ≥+50% | W−1 ≥20 次曝光；否则只显示为「小基数曝光上升」 |
| 从零起量（基线未观测到） | W−1 明细里没有这部剧的行，W0 ≥20；未经逐剧核对时显示为「新出现，基线未核对」 | 全站层 `usable`；Vh 与明细在 W−1 都没有观测到这部剧，在 W0 一致且 ≥20。含义是「前一窗口在 GSC 返回的数据里未观测到」，不断言真实为零 |
| 高点击率 | W0 点击 ≥50 且 CTR ≥5% | 同条件 |
| 排名冲顶 | 加权排名 4–20，且 Q 里出现剧名 + 意图词 | W0 曝光 ≥50；Q 与 W0 取同一个 PT 日；只作全站证据，不说明任何国家 |

**7 天 `rising`**：W0 曝光 ≥100、比值 ≥1.5、增量 ≥30。进智能体前要过日级两层准入：14 个 PT 日逐日的全站层 `usable`，且 Vd 与明细一致。过度离散的率检验 p 值与 BH 校正结果**只作质量注记**展示，不作隐藏门槛。

- CTR = 总点击 ÷ 总曝光；排名按曝光加权。
- **不给因果标签**。只写「曝光上升」，再附「伴随平均排名改善 ≥2 位」或「未伴随排名改善」，以及「原因未定」。曝光变化也可能来自收录、页面迁移、查询组成、结果样式变化，平均排名没变不能证明需求增长。
- 阈值在影子运行期间按国家报告实际命中数、小基数占比、人工判定的误报与漏报，再回标。09-03 一天的全站快照不能完成欧美阈值校准。

## 6. 双通道联动、运营动作与提前量

### 6.1 联动（`link-rules-v1`，纯函数，版本冻结进候选集）
**只在同一个国家内联动**：Trends 的 US 对 GSC 的 USA，GB 对 GBR，ES 对 ESP，DE、FR、IT、MX、BR 同理；Trends 的 WW 和 GSC 的全站合计只并列显示为「全球同向」，不算双涨，也不给建议动作，因为两边可能涨在不同国家。没有共同国家的，显示「不同市场信号」。

| Trends（该国） | GSC（同一国） | 标签 | 建议动作（只提示，不自动执行） |
|---|---|---|---|
| confirmed rising | 曝光上升或从零起量，过正式门槛 | 双涨 | 进发布清单；生成「可粘贴」行 |
| confirmed rising | ReelShort 行有页面、曝光低 | 站外先行·补页 | 写博客、补内链、提交索引、进切条候选 |
| confirmed rising | 其他剧场行，本站没有页面 | 站外先行·仅分发 | 进 YouTube 等渠道切条候选 |
| 未观察或低量 | 曝光上升或从零起量 | 站内独涨 | 先核对同名与 URL 迁移；自动进 B 档 |
| cooling | 任意 | 退潮 | 只拦截该国的「加码」建议 |
| 发现命中，池外 | — | 池外发现 | 资料页人工找片源，或通知 RealShort 导入 |

- **时效**：联动时 Trends 集合不超过 26 小时、GSC 集合不超过 6 小时，GSC 的 W0 与 Trends 的 B6 相隔不超过 48 小时；否则显示「时效不符」。
- **降级**：GSC 退到 `[hour,page]` + 日级国家时，24 小时窗口没有国家维度，按国家的 24 小时联动停用，只用 7 天日级数据按国家联动。
- 带 `migration_suspect`、`mapping_changed`、`gap_exceeded`、`unverifiable`、`unstable` 的不进联动。
- YouTube 发现不算网页搜索的需求确认。

### 6.2 提前量：四个指标，所有提示都进分母
- **起点**：集合的发布时间，也就是用户实际能看到提示的时刻。`first` 和 `confirmed` 分开算。
- **提示记录**：每次提示写进 `ggwp_obs_alerts`，保留 180 天，不随集合清理。去重键 = 身份（沿冻结的别名版本）× 通道 × 状态 × 国家或 geo；同一键 14 天内只记第一次。每条保存当时判定行的全部中间量，作为证据快照。
- **预先指定的后续事件**：进入 v1 候选池、首次出现榜单证据、GSC 越过「从零起量」或 rising、`promoters_cnt` 上升（镜像上线后）、进入编辑精选表。清单写进 `eval-rules-v1`，改清单要升版本。
- **四个指标**

| 指标 | 算法 |
|---|---|
| 池外发现延迟 | 发现段首次命中池外剧名 → 它首次进入共享池 |
| 池内预警提前量 | 在提示前后各 14 天里找该身份的后续事件：提示前已有事件的记为滞后（负值，取最早那个）；否则取提示后的第一个；都照样统计 |
| 未兑现率 | 提示发布满 14 天仍没有任何后续事件的比例；分母是满 14 天的全部提示，不满 14 天的单列「观察中」 |
| 人工忽略率 | 资料页里被人工标「无关」的比例 |

- **里程碑要从上线当天开始记**，同样保留 180 天：gsc 服务每轮读当前共享批次，把变化增量写进里程碑表；上线当天给每个身份记一条「上线前已存在」的初值。旧批次会被 `prune_shared`（gp/repository.py:641）删掉，不能事后补算。
- **复盘**：每周汇总；至少 30 件提示才下结论。四周后池内预警提前量中位数 ≤0、或未兑现率超过你定的上限时，Trends 降为旁证；不足 30 件就延长观察。

### 6.3 延迟时间线
- 20:30 UTC 起跑，窗口在 D−1 约 17:00 UTC 结束（金丝雀期 22:00 起跑时是 19:00）。
- D 日 02:00 UTC（北京 10:00）目标发布，此时是 `first`。
- D+1 日的集合再次成立才是 `confirmed`。B 档升 A 档再加 1 天。
- 标准说的「提前 24–48 小时」仍是待验证的假设。

## 7. 数据合同与版本冻结

### 7.1 钉住与冻结
- 不在四元组后面追加字段（gp/context.py:38-42 按四元组解包）。另建 `ObsPin(trends_set_id, gsc_set_id)`，在当前 pin 的同一条 SQL 里用两个标量子查询取出，`SelectionService.query` 冻结到候选集的三个新列。
- **集合里冻结的输入**：来源剧库批次、别名版本、旧页解析快照 `snapshot_id`、`market-map` 版本、规则版本与全部参数、`collector_version`、各切片的 metadata 与状态。
- **候选集另记**：`link-rules` 版本和排序版本。`sort=obs` 要在 `gp/selection.py` 登记独立的 `ranking_version = obs-v1`；现有代码会把非 rank 排序记成 `evidence-date-v1`（:187 起），必须改。
- **只读判定行**：资料页详情和智能体只读 `ggwp_obs_states`，那里存着每个结论的全部中间量和原始计数。它们不回查会被覆盖的小时表或会过期的原始表，所以明细表被覆盖或清理，旧结论照样能复现。
- **语义兼容检查**：钉住时核对集合的来源剧库批次与候选集的剧库批次。相同就直接用；不同时，两批都有的身份直接沿用，其余按集合冻结的别名版本映射，映射不到的标 `set_batch_mismatch`，不进结果。映射结果写进候选集的证据里，之后不重算。
- **历史版本的执行**：`sort=obs` 与 `link-rules` 都按版本登记实现，候选集记下版本；换一批时用记下的版本执行，代码里找不到这个版本就拒绝，与现有 `RULE_VERSION` 的校验同一做法（gp/selection.py:187-190）。候选条目里的 `obs_*` 证据（含联动标签）在查询当时物化，重读不重算。
- 换一批沿用父结果的集合；父集合已被清理报「已过保留期」；父结果没有集合、本次却带了趋势条件，直接拒绝。
- 三层版本各自独立：采集合同 `collector_version`、判定规则 `trend-rules-v1` / `gsc-rules-v1` / `link-rules-v1`、候选引擎 `RULE_VERSION`（gp/selection.py:11，不改）。

### 7.2 身份连续性
- **现状**：本地 09-21 批次 4416 行里，715 行的身份用标题 slug 拼成（KalosTV 593、FlickReels 103、MoboReels 12、StarShort 6、DramaBox 1），63 行 ShortMax 的 ID 带「（已设置定时）」这类备注，合计 778 行、17.6%。这是本地库的计数，不是生产上的变动率。规则见 RS:scripts/juyuantai/build.py:695-704：有 id 用 id，没有用标题 slug + 语种 slug，重复追加 -2、-3。标题一修订、同名顺序一变、备注一去掉，身份就会变。
- **自动接收只限稳定上游 ID**：两批之间，去掉括号备注后上游 ID 完全相同、平台和语种也相同的，记 `auto` 别名。
- **标题匹配只出建议**：平台、规范化标题、语种都相同的消失行与新增行，只生成 `suggested` 别名，进资料页的待确认队列；人工确认后才归并。标题真正修订的情形靠人工在队列里手动配对。
- **拒绝**：环、多对多、跨平台、跨语种的别名一律拒绝。
- **追加式、带版本**：别名表只追加，每次变更产生新版本；集合冻结它用的版本，旧结论不随后来的别名变化。
- **上线前核实真实变动率**：比较生产上两个共享批次的身份集合（只读，先问你）。
- **建议 RealShort 改源头**：build.py 生成 id 时去掉括号备注（那边仓库的改动，需你批准）。KalosTV 这类没有上游 ID 的平台只能靠建议队列。

### 7.3 条件、排序与剧库范围
- `PickConditions`（gp/contracts.py:122）新增 `trend_state`（rising/emerging）、`trend_geos`、`trend_include_first`、`gsc_state`（rising/surge/from_zero/high_ctr/rank_push/present）、`gsc_countries`、`link_state`。每个国家单独判定，任一国家满足即命中；工具名单不变。
- **排序**：带观测条件时用 `sort="obs"`（`obs-v1`）：先按最好的状态（confirmed > first > 只有 GSC 正式标签），再按命中国家数，再按最新的 `window_end` 或 GSC 截止，最后按 identity；多个国家命中时取最好的那个国家的状态。不按指数。默认的依据日期排序（gp/selection.py:121）与趋势无关，不能用。
- **只对共享剧库**：当前剧库取个人和共享批次里发布时间最新的那个（gp/pin.py:56-65），个人导入之后发布的共享批次会重新成为当前批次。观测集合按共享批次的身份算，所以带观测条件时要求钉住的剧库是共享批次，否则拒绝并提示。
- **只在设置时写入**：`conditions_json=effective.model_dump()`（gp/selection.py:258）会把默认值全部写进卡片；未设置的观测字段要去掉。原因：`listPickResults`（fe/core/pick/api.ts:102-109）对整个会话做 strict 解析，一张新形状的卡会让整个面板报错。

### 7.4 结果、提示词与核对
- `candidate_item` 追加 `obs_trends`、`obs_gsc`、`obs_discovery`，放在现有 evidence schema 里，不加 payload。`result_view` 只加一个 `observations` 键：集合 id、截至时刻、剧库批次与观测集合的身份覆盖率、各质量档被排除的条数。
- 提示词（gp/middleware.py）加四句：只能说「按 vX 规则、截至 T、在某国家被判为上升观察」，不说热度数值、不说爆款、不说需求原因；`obs_gsc` 与 v1 的 `gsc` 信号不是同一口径；`obs_*` 不是 signal_kind；有被排除的条目时不能说「没有剧在涨」。
- `check_answer` 加 `trend_checked`，触发词只认「谷歌/Google/搜索（趋势|热度）」「站外（热度|趋势）」，避免误报榜单回答；用现有回答样本回归。

### 7.5 发布顺序
1. 前端放行可选字段，新旧夹具与混合会话都能解析；
2. gateway 带上 0007，集合为空时返回「趋势数据尚未就绪」；
3. cron 服务上线，发布开关关着；
4. 阶段 0 与金丝雀通过后打开开关；
5. 最后改提示词。
