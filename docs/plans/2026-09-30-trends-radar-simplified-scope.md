# 选剧工作台趋势雷达简化版范围（2026-09-30 用户批准）

**这份文档是什么**：2026-09-30 用户认为原方案（[设计 v2](2026-09-25-trends-radar-design.md)、[实现计划](2026-09-25-trends-radar-impl-plan.md)）相对需求做重了，要求缩减。用户的原话是「只想通过 Google Trends 辅助找到热门剧集，或者从我们的热门剧集里找出在 Google Trends 上同样热门的」。本文是缩减后的范围，经 gpt-6-astra 只读审计一轮（结论「改后可交」，处置见第 11 节），用户已批准（第 8 节）。

**与原文档的关系**：范围、任务与上线步骤以本文为准；原设计与原计划保留作记录，被搁置的部分在实现计划第 8.2 节列出。已上线的 S0 到 S6 和已写好的采集程序照常使用，运行与部署仍按 `docs/pick-workbench/observe-runbook/` 的手册。

代码事实核对于 `ggwork/main` c91b647a。

## 1. 目标

每天早上在资料页看到一张表：我们自己数据里最热的一批剧，各自在 Google 上近 30 天的搜索走势，哪些在涨、哪些在落、哪些查不到。

这张表只做辅助参考。它不自动做任何决定，不进智能体，不改候选排序。

## 2. 用户看到什么

资料页的 trends 页签，一张表，每行是一部剧的一个语种剧名：

| 列 | 内容 |
|---|---|
| 剧 | 剧名、平台、语种 |
| 入选依据 | 哪个榜、哪一期、第几名；或 ReelShort 收入排第几 |
| 走势 | 近 30 天的小曲线，没有数据的日子断开，不画成 0 |
| 近 7 日均值、前 7 日均值 | 两个数，只算完整日 |
| 变化 | 近 7 日相对前 7 日的百分比；前 7 日为 0 时不算百分比 |
| 标签 | 上升、回落、持平、新出现、数据太少 |
| 采集结果 | 有数据、Google 未返回数据、这晚未查到 |
| 提示 | 剧名较短时提示「搜索热度可能不属于这部剧」 |
| 链接 | 点开就是 Google Trends 上这个词的页面 |

- 排序：按变化，或按我们这边的入选顺序。
- 表头写明：采集日期、这晚计划查多少部、多少部有数据、多少部未返回数据、多少部未查到。
- 这张表由当晚的任务清单驱动：清单上的每部剧都占一行。当晚没查到的剧显示「这晚未查到」，不拿前几天的旧曲线顶替。
- 采集漏跑、数据过期时页面顶部有红色提示。

## 3. 每晚怎么跑

1. **取剧**（共 N 部）：
   - 先取带名次的三个榜各自最新一期的全部剧：鹊娱转化榜、鹊娱收入榜、Kalos 日榜。各榜分别取，不把不同榜的名次混在一起排。
   - 按剧的身份去重。
   - 不够 N 部时，按 ReelShort 最新的收入数字从高到低补足。
2. **查询**：每部剧查一次，用完整剧名（只清洗标点和配音标记），日级，近 30 天，地区为全球。每部剧 2 个请求，不查相关搜索。
3. **存储**：原始曲线进现有的原始表。查不到就如实记录，不补 0。
4. **时间**：沿用现有安排，UTC 17:30 起跑，01:45 截止，北京时间上午 10 点前出表。

N 取 100，对应 200 个请求。

## 4. 标签怎么定

标签只描述表里那两个均值的关系，不套用 v9.5 的门槛。

| 标签 | 条件 |
|---|---|
| 数据太少 | 近 7 个完整日里不为 0 的天数少于 3 |
| 新出现 | 前 7 日均值为 0，近 7 日均值大于 0 |
| 上升 | 变化不低于 +25% |
| 回落 | 变化不高于 −25% |
| 持平 | 其余 |

按表中自上而下的顺序判，先命中的为准。Google 没有返回值的日子不参与均值。

±25% 和「少于 3 天」两个数集中写在一处，上线后看第一周的真实数据再调。

为什么不用 v9.5 的五种状态：那些门槛是按 7 天小时级窗口定的。搬到 30 天日级窗口上会系统性误判，例如一部剧前 4 天为 0、后 3 天是 10、20、30，明明在起量却会先被判成噪声。用两段均值的比值，不受 Google 归一化基准的影响。

## 5. 不做的

| 不做 | 原因 |
|---|---|
| GSC 站内数据整条线 | 另一个独立需求，还要等服务账号；以后要做再单独立项 |
| 智能体的趋势条件、obs 排序、候选卡证据 | 超出「辅助参考」 |
| 集合冻结、回放、发布开关、两周影子运行 | 只读参考表不需要 |
| v9.5 的五种状态和逐日环比 | 见第 4 节 |
| 小时级数据和日内活跃时长 | 实测已知热门剧小时级 8 部只看得见 1 部，还多花一倍请求 |
| 平台词上升搜索、发现队列、池外命中匹配、别名与歧义的人工确认 | 实测一次返回 23 条里像剧名的只有 1 条 |

| 同一部剧多个地区、多语种剧名自动归并 | 每个语种剧名各占一行，由人看 |
| 跨剧可比的锚点对比 | 见第 7 节「相对值」 |

## 7. 已知限制

1. **它是查询参考，不是筛选器**：阶段 0 日级实测，已观测的 7 部已知热门剧里只有 2 部看得见。这够支持做一张参考表，不够证明它能筛出 Google 上的热门剧。
2. **覆盖量有限**：一晚 100 部。预算上限是 165 部（留给查询的 330 个请求除以 2），实际能跑完多少取决于限流。
3. **多数剧可能查不到**：用户提供的现有看板（`dashboard(1).html`，4,442 行）里 4,211 行是「暂无显著搜索」，有明确状态的 23 行。我们取的是最热的一批，比例应当好一些，但没有实测过。
4. **指数是相对值**：每部剧以自己 30 天内的峰值为 100，不能用来比较两部剧谁的搜索量更大。所以表里不按指数排序，只按变化排序。
5. **剧名歧义**：「剧名较短」只是提示，既会漏（例如 `Is It Just Me?`）也不能证明搜索的就是这部剧。看板那 23 行里约一半是 `女王`、`Stay`、`灰姑娘` 这类词。
6. **出口还没验证**：Railway 的出口会不会被 Google 拦，要等采集真正跑起来才知道。本机两天测试都在前 60 个请求内被限流过。
7. **全球地区没有实测过**：选它是因为与现有看板一致。第一周如果查到数据的比例很低，再改成按语种的主市场查。
8. **数据滞后一天**：最新一天是最近的完整日，通常是昨天（UTC）。
9. **我们自己的榜单薄且可能过期**：三个榜合计至多约 59 部（鹊娱两榜各 25，Kalos 日榜 09-22 约 9 部），去重后更少；上游自动榜单采集 09-28 起还没恢复。所以大部分名额会由 ReelShort 收入补足，入选依据一列会写明榜单是哪一期的。
10. **ReelShort 收入是滚动 30 天的数**：它反映近一个月的总量，不是近 7 天的。

## 10. 上线顺序

1. **切 cron，canary1 验证出口**（现在就能做，不依赖新代码）：
   - 有效夜晚：通过了负载闸门、实际发出请求的夜晚。被闸门拒跑的夜晚不算数，也不算失败。
   - 通过：累计 3 个有效夜晚，没有出现验证码或同意页，没有因限流被停用。
   - 停止：出现验证码或同意页就停 cron，由用户决定下一步（官方 API、代理或放弃）。不靠切换模式绕过去。
2. 开发第 6 节第 1 到 8 项，合进主线。
3. 部署 gateway 和 cron（cron 同时切到新任务来源并改变量），再部署前端。
4. 第一周看真实数据：查到数据的比例、标签是否合理，按需调整第 4 节的两个数和地区。

每一步对外操作照旧先经用户同意。止损方式不变：停 cron，不回退镜像，不动库。
